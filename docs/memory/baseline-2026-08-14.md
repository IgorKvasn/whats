# Startup memory baseline — 2026-08-14

Reference point for later memory work. Compare against this, not against a
one-off reading from a system monitor.

| | |
|---|---|
| App version | 1.16.2 |
| Commit | `8a4477d` |
| Electron | 43.2.0 |
| Scenario | `startMinimizedToTray` enabled, **main window never opened** |
| Profile | developer's real profile (`~/.config/whats`, 1.3 GB on disk) |
| Hardware acceleration | disabled (`hardwareAccelerationEnabled: false`) |
| Runs | 3, averaged |
| Readings | T+10s and T+60s after launch |
| OS | Ubuntu 26.04 LTS, kernel 7.0.0-29-generic, 45 GiB RAM |

Reproduce with `npm run measure-memory -- --at 10,60`, following the protocol
in [`README.md`](./README.md). Every run landed within 0.1s of its target, and
no process had any swap, so the resident figures are the whole cost.

## Headline figures

Mean of three runs. Process tree is 9 processes in every run.

| Reading | Summed RSS | Summed PSS |
|---|---|---|
| **T+10s** | **1153.2 MiB** | **643.1 MiB** |
| **T+60s** | **1045.6 MiB** | **532.6 MiB** |

**A system monitor displays the summed RSS figure** — so the number a user sees
and complains about is roughly **1.1 GB**, while actual memory pressure is
about **530–640 MiB**. Pages shared between Electron's processes, and so
counted more than once in the displayed figure, are 44% of it at T+10s and 49%
at T+60s.

Memory *falls* between T+10s and T+60s (108 MiB RSS, 110 MiB PSS) as the
renderers finish loading and release transient allocations. A change measured
at T+10s must be compared against the T+10s baseline, never the T+60s one, or
it will appear to save ~110 MiB it did not save.

## Observations for later tickets

These are starting points for investigation, not conclusions — this ticket only
establishes the baseline.

- **The renderers dominate**, at 64% of PSS at T+60s. They are also where the
  whole T+10s→T+60s drop happens; every other process type is flat to within
  2 MiB across both readings.
- **Two renderers exist even though the main window is never opened.** Worth
  identifying the second one before assuming either can be removed. This
  harness reports renderer type and PID but not which view a renderer backs,
  so answering this needs either `getAppMetrics()` or process-level digging —
  see the note in [`README.md`](./README.md).
- **A GPU process runs despite hardware acceleration being disabled**, costing
  25 MiB PSS. `app.disableHardwareAcceleration()` does not by itself stop the
  GPU process from launching.
- **The browser process holds 107 MiB PSS** with no window shown.
- The three zygotes together cost 23 MiB PSS but 124 MiB RSS — a 5.4x ratio,
  the clearest case here of the displayed figure overstating real cost.
